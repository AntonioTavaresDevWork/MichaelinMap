# Michaelin Map

A places guide curated by one person. Restaurants, bars, food trucks, shops, hotels, parks and
attractions — each one carrying an explicit quality verdict and a set of tags describing not just
what a place *is*, but what it is *for*.

This is a personal project. It is not a SaaS product, it has no customers, it will not be
monetized, and it is not indexed by search engines. It exists so that one person's judgment about
511 places becomes something he can share with a link.

> **The judgment layer is the only irreplaceable data in this system.**
> `tier`, `starred`, `the_dish`, `curator_note`, `story`, `last_visited` and the assignments in
> `place_tags` are the whole point of the product. No automated routine writes to those fields
> without explicit authorization from the owner. In any trade-off, the judgment wins.

## Live

**https://michaelin-map.vercel.app/**

Deployed on Vercel from `main`, built from the two `VITE_` variables set in the project's
environment. **Deliberately unlisted** — `robots.txt` and a `noindex` meta tag both say so (ADR-07).
Michael hands the link to people; search engines do not.

The SPA rewrite in `vercel.json` is what makes a shared deep link work. Without it,
`/city/austin` returns 404, which is exactly the shape of a link someone was sent.

## Status

Live since S14. All seven MVP features are complete: foundation, schema and data import, admin, public guide,
faceted filters, Codes with Roulette, and field reports. The database holds 511 places, of which
58 are published.

**The app has never been deployed.** `vercel.json` is committed and the repository is ready, but no
hosting is configured. See "Handover" below.

## Getting started

Requires **Node 22 or newer** (`engines.node` enforces it; the project was developed on 24.19.0).

```bash
git clone https://github.com/AntonioTavaresDevWork/MichaelinMap.git
cd MichaelinMap
npm install
cp .env.example .env.local   # then fill in VITE_SUPABASE_ANON_KEY
npm run dev
```

`.env.local` is required, not optional: the Supabase client validates its environment at import
time, so a missing key fails the app at startup rather than at first query. `.env.example` already
carries the project URL — only the anon key is missing, and it is not a secret (it ships inside the
browser bundle by design).

Without access to the Supabase project, the app will build and run but show nothing. Getting that
access is part of the handover, not of the setup.

| Script | What it does |
|---|---|
| `npm run dev` | Vite dev server |
| `npm run build` | `tsc -b && vite build` — the type check is part of the build |
| `npm run lint` | **oxlint**, not ESLint. Config in `.oxlintrc.json` |
| `npm run preview` | Serves the production build from `dist/` |

`build` and `lint` must both be clean before any commit. There is no test suite — see "Known gaps".

## Project layout

```
src/
  components/{ui,admin,public,layout,auth}   ui/ is generated by shadcn — check before writing custom
  hooks/                                     one custom hook per data concern
  lib/                                       supabase client, filters, code effects, roulette, utils
  pages/{public,admin}/
  types/                                     database types, snake_case (see below)
supabase/
  migrations/                                the schema's source of truth
  rollbacks/                                 one per migration
docs/                                        product bible, status, backlog, origin material
.claude/                                     agent instructions, skills, boot checklist
```

Data flows in one direction: component → custom hook → React Query → Supabase client → PostgreSQL
with RLS. There is no server of our own; `supabase/functions` does not exist because nothing has
needed it yet.

**Types are `snake_case`** because objects populated by a direct `select('*')` are never converted
by supabase-js. Where a mapping to `camelCase` happens, it happens at the data-access boundary and
nowhere else.

The `@/` path alias resolves to `src/`, declared in `vite.config.ts` and in the `tsconfig*.json`
files through `paths` **without `baseUrl`** — TypeScript 6 deprecated it.

## Stack

React 19 + Vite 8 + TypeScript 6, as a single-page app with no SSR. **This is not Next.js**: there
is no App Router, no server actions, no API routes.

Tailwind 4 and shadcn/ui for the interface. **MapLibre GL 5.x** with OpenFreeMap tiles for the map —
chosen because it swaps map styles at runtime, which the Codes feature depends on, and because it
does not charge per render. Supabase (PostgreSQL 17 + Auth) for the backend, React Query for server
state, React Router for routing, Zustand where UI state needs it, `sonner` for notifications,
`lucide-react` for icons, and Nominatim/OpenStreetMap for the geocoding in mobile quick-add.

Deliberately absent, each for a recorded reason: Google Places API, Google Maps embeds, SSR or
pre-rendering, react-hook-form, zod, and TanStack Table.

## Database

The schema lives in `supabase/migrations/`, and every migration has a matching rollback. Naming is
`YYYYMMDDNNNNNN_description.sql`, and each file wraps its work in an explicit transaction with
numbered blocks and inline validation gates that abort the transaction when an assumption fails.

Four migrations are live. They build eight tables with RLS enabled on all of them, then seed the
vocabulary and import all 511 places from the master CSV: 4 tiers, 94 tags, 38 field-report
questions, and 173 machine-suggested tag assignments.

Two rules that have already cost a failed apply between them, so they are worth knowing before
writing SQL:

- **The `GRANT`/`REVOKE` block always goes last.** Supabase applies default privileges at the moment
  an object is created, so revoking before creating leaves the new object fully exposed.
- **Introspect before you write.** The bible describes the target; only the live database describes
  what is there. Convention is not a substitute for looking, and a column that exists in one table
  under a familiar name may not exist in the next.

Migrations are applied through the Supabase MCP server from a Claude Code session, which rewrites
the `version` column and therefore requires manually realigning `schema_migrations` afterwards. The
`.claude/skills/michaelinmap-migration` skill documents the whole procedure, including what to do
when a payload is too large to apply in one call.

## Authorization

There are two roles and no third one. **Visitors** have no account and no login; they read published
content and may submit field reports. The **curator** logs into `/admin` and writes everything else.

Authorization is a **curator allowlist**, not tenancy and not RBAC: a row in `curators` keyed to an
`auth.users` id, resolved by an `is_curator()` function that every RLS policy calls. Signup is
expected to be disabled in the Supabase project. An authenticated account that is not in the
allowlist is treated exactly like an anonymous visitor — verified end to end with simulated JWTs, in
both directions.

Two paths are deliberately public, and both go through a function rather than a table:

- `rpc_redeem_code()` — validates one code at a time. `codes` has no public SELECT at all, and every
  failure answers identically so the function cannot be used to enumerate codes.
- `rpc_submit_field_report()` — the only way a visitor writes anything. It derives the publication
  status on the server from the question's own configuration, truncates free text, and rate-limits
  by session. Anonymous callers have no INSERT privilege on the table, so this is enforced at the
  privilege level and not only by policy.

## Handover checklist

Cloning this repository reproduces the application. It does **not** hand over the project. Three
things live outside git and have to be granted by a person.

**1. Repository access.** `AntonioTavaresDevWork/MichaelinMap` is private, so the new maintainer
needs a collaborator invitation. Note that `AdminFeedpro/MichaelinMap` is an earlier home that was
abandoned at its first two commits — it is not the remote, and cloning it gets you almost nothing.

**2. Supabase project access.** Without an invitation to the project there is no dashboard, no MCP
server, no way to apply a migration and no way to reset the curator's password. This one is expected
to be temporary: the database is currently hosted in a personal Supabase account and moves to the
company's organization on handover. See "Moving to a different Supabase project" below.

**3. A curator account.** Do not pass the existing password around. Create a new account in the
Supabase dashboard and add its row to `curators` **through a versioned migration**, resolving the id
by a subquery against `auth.users` rather than hardcoding a UUID —
`20260806130000_f01_seed_curator.sql` is the pattern to copy.

Three files are gitignored on purpose and each needs its own treatment:

| File | Treatment |
|---|---|
| `.env.local` | Copy from `.env.example` and add the anon key |
| `.mcp.json` | Holds a personal Supabase access token. **Never share an existing one** — the new maintainer generates their own. `docs/how-to-supabase-mcp-claude-code.md` explains how |
| `.claude/settings.local.json` | Local tool permissions. Disposable; it regenerates |

**Back up the database before handing anything over.** Today the migrations reproduce the database
almost completely, because every write so far arrived through one. That stops being true the moment
curation begins: written verdicts and confirmed tags will exist only in the database and in no
migration. A clone of this repository with the database lost gives you a working app with nothing
irreplaceable inside it, which by the terms of this project is the same as having nothing.

### Moving to a different Supabase project

The database and the hosting both live in personal accounts today and are expected to move to the
company's organization when the project changes hands. Keep them in the same organization — split
ownership is how a project ends up with nobody able to rotate a key.

**Most of it rebuilds from this repository.** Applying the four migrations in order to an empty
project reproduces the schema, the RLS policies, both public functions, the whole vocabulary and all
511 places, because the seed and the import are themselves migrations. That is the point of having
built it that way. Three things do not come along, and each has bitten in a predictable place.

**Auth accounts do not travel.** `auth.users` belongs to Supabase, not to our schema, so no migration
recreates it. Create the curator account by hand in the new dashboard with auto-confirm enabled
**before** applying `20260806130000_f01_seed_curator.sql`: that migration resolves the account by an
email subquery and its first gate raises, aborting the transaction, when no confirmed account
matches. If the new curator uses a different address, edit the email in that migration — do not
replace the subquery with a literal UUID, which is exactly the latent bug the subquery exists to
avoid.

**No migration publishes a place.** Every place is created `unreviewed`, and the launch batch of 58
was an ad-hoc `UPDATE` against the live database. A freshly rebuilt project therefore holds all 511
places with none published, and the public guide renders empty while looking perfectly healthy —
city gate included, since it counts published places. The criterion is recorded: the batch is every
place that is starred or carries the `destination` tier. Re-applying it is one statement, and this
time it is worth writing as a migration so the next rebuild does not rediscover this.

**Project settings do not travel.** Disabled signup, leaked-password protection and anything else
toggled in the dashboard are per-project. Re-apply them and re-run the security advisors against the
new project; the previously accepted `SECURITY DEFINER` warnings will reappear and are explained in
the backlog.

**If curation has already started, do not rebuild — migrate the data.** Written verdicts and
confirmed tags exist in no migration, so a rebuild silently discards them. Dump and restore the
`public` schema only, leaving `auth` alone, and create the curator account first. Watch
`places.updated_by`: it is a foreign key into `auth.users`, and ids from the old project do not exist
in the new one, so those values need to be nulled or remapped before the restore will hold. After
applying migrations through the MCP server, realign `schema_migrations` as the migration skill
describes.

**Where the project's identity is written down.** Repointing the app means changing all of these:

| Where | What changes |
|---|---|
| `.env.local` | Both `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` |
| `.env.example` | The URL is hardcoded here. Miss it and every future clone is seeded with the old project |
| `.mcp.json` | Project reference plus a personal access token, generated by whoever owns the new session |
| `.claude/CLAUDE.md` | The project identity block near the top |
| `docs/MICHAELINMAP_BIBLE.md` | Section 3, repository and infrastructure |
| Hosting environment | The same two `VITE_` variables, once a deployment exists |

Leave the historical mentions in `docs/STATUS.md` alone. That file is a session log, and rewriting
what a past session observed would make it useless as a record.

**Then verify through the front door, not through the dashboard.** Read the guide with the new anon
key and confirm that an anonymous caller sees exactly the number of published places you expect and
no more, that `codes` refuses to be listed, and that a logged-in curator can write. That check has
caught real authorization mistakes in this project twice; the dashboard, which reads as an
administrator, would have shown nothing wrong either time.

## Known gaps

Recorded honestly, all of them tracked in `docs/BACKLOG.md`.

- **No test suite.** Three throwaway harnesses have verified filters, codes and field reports
  against the live database, and none was kept. Anyone changing that logic works without a net. The
  backlog holds the technique the harnesses used, which is also the outline of the suite when it
  gets written.
- **Two admin screens have never been used.** `/admin/codes` and `/admin/reports` compile and pass
  the linter, and their queries were validated against the database separately, but nobody has
  clicked through them while logged in.
- **The main bundle exceeds Vite's 500 kB warning.** The map is already lazy-loaded so that opening
  the city gate does not pay for it; splitting admin from public is the next obvious step.
- **Accessibility is partial.** Contrast is solved at the source — every Code theme derives its text
  color from the WCAG luminance of the color the curator picked, so no theme can be born
  illegible — but keyboard navigation through the filters and a screen-reader path for the map's
  information are still open.
- **Curation has not started.** Every tag assignment in the database was suggested by machine, and
  none has been confirmed. Suggested tags are hidden from visitors until confirmed, so the public
  filter panel shows fewer facets than the vocabulary allows. This is content work by a specific
  person, not a task waiting on code.

## Troubleshooting

**The dev server answers on the network URL but not on `localhost`.** On the machine this project
was built on, Chrome refuses both `localhost:5173` and `127.0.0.1:5173` while the port is
demonstrably listening, and answers only on the address Vite prints as `Network`. Use that one
before assuming the server failed to start.

**The map shows pins but no streets or water.** Reported and investigated at length: the geometry
renders correctly in ordinary browsers, including Firefox and mobile, and fails only in the
automated Chrome instance driven from the CLI on that one machine. WebGL, web workers, page-level
network, style, sprite, fonts and two MapLibre versions were all ruled out with evidence. Read the
relevant backlog entry before spending any time on it — the whole path has already been walked.
